## 2. 残留风险(逐条带证据)

### #19 pugixml header-only 全 TU 内联(KNOWN_ISSUES #19)

`StdAfx.h:82-86` 的接入方式意味着:DuiLib 每个 TU(以及 mlaunch 每个 `#include <UIlib.h>` 的 TU)都内联一份 pugixml 实现(inline COMDAT)。后果与约束:

- 编译时间与目标体积税;调试器里 pugixml 栈每 TU 一份;
- **不能**再把 `pugixml.cpp` 编进来:独立 TU 无 `PUGIXML_HEADER_ONLY` 宏会产出强符号,shared 链接直接 LNK2005/LNK1169(static 也冗余)。fork 的 `add_files("DuiLib/**.cpp")` 类 glob 已排除之;mlaunch 的 `DuiLibLite` 因 3rd/ 迁移后 glob 覆盖不到 `3rd/pugixml/pugixml.cpp` 而天然无需排除(mlaunch xmake.lua:38 注释)——但**内联本身仍在**;
- 转独立编译必须先改 `StdAfx.h`(去掉 HEADER_ONLY、提供 includedirs)——该头是全库共用的,任何改动都是与上游合并的高敏感区,故 LOCAL_CHANGES 明确"待与上游合并策略一起定"。

### #20 ATL 依赖:atlimage.h(KNOWN_ISSUES #20)

`DuiLib/UIlib.h:158` 无条件 `#include "Control/UIImageBoxEx.h"`,后者第 4 行 `#include "atlimage.h"`。VS 未装"适用于 v143 生成工具的 C++ ATL"组件时,**任何包含 UIlib.h 的 TU 直接 C1083**;GitHub runner 自带 ATL,所以 fork CI 掩盖了本机问题。当前规避=本机装 ATL 组件(装完须删 `%LOCALAPPDATA%\.xmake\cache\detect` 重探测,`xmake f -c` 清不掉);根治=`UIImageBoxEx.h`/ControlFactory 的 `CImageBoxExUI` 注册加 `DUILIB_NO_IMAGEBOXEX` 门控(mlaunch 不用该控件)。

### 其他残留

- **SDL 头文件的宏门外包含**:`StdAfx.h:124-158` 的 `#include <SDL3/SDL.h>` 虽在 `DUILIB_SDL` 内,但整段在 StdAfx.h 里——意味着 SDL 路径一旦启用,所有 TU 都要能找到 SDL 头;mlaunch 以整组排除 `*Sdl.cpp/*SDL.cpp` 规避(xmake.lua:42-43),排除清单须与 fork 根 xmake.lua 持续同步。
- **zip/unzip**:`DuiLib/Utils/unzip.cpp`(zip 资源包支持)被 mlaunch 排除(xmake.lua:36),核心渲染不需要;保留在 fork 供 XML 皮肤 + zip 资源场景。
- **测试基建为零**:fork `tests/` 仅一个孤立头文件(KNOWN_ISSUES #18),库级回归只能靠四矩阵编译。

## 3. "第三方库提取独立"的最终结论

**结论:对 mlaunch 所需的 Win32/GDI 核心,"第三方提取"已基本完成,方向正确;剩余工作是收口而非搬运。**

依据:

1. 核心库真正的第三方依赖只有 3 个(pugixml/nanosvg/stb),全部已迁入 `3rd/`,一库一目录 + `LOCAL_CHANGES.md` 差异登记 + xmake 接线位,与核心源码物理解耦;
2. 其余大件(SDL 全家/CxImage/Scintilla/AngelScript,合计百万行级)对核心**零依赖**,已按"应用层自取/暂不迁移"分类登记,不需要也不应该搬进核心构建;
3. fork 对核心的实质改动收敛在 6 个提交内(渲染修复 c329337、工程化 4f355ce、三次 3rd 迁移、登记表 f89c4f7),mlaunch 以 submodule 钉在 f89c4f7(`git submodule status`:third_party/DuiLib_DuiEditor @ f89c4f78,分支 refactor/extract-3rd),glob `DuiLib/**.cpp` + 同步排除表,源码编译、无预编译产物——**提取的边界与 mlaunch 的消费面完全对齐**。

### 剩余步骤清单(按优先级)

1. **[编译方式] pugixml 从 header-only 转独立 TU**:改 `StdAfx.h:82-86` 为普通 include + xmake 增加 pugixml 编译 target/includedirs;前提是与上游合并策略一起定(改动公共头)。转 xrepo(`add_requires("pugixml")`)同此路径。
2. **[ATL 去除] `DUILIB_NO_IMAGEBOXEX` 门控**:`UIlib.h:158` 的 include 与 ControlFactory 注册条件化,使无 ATL 组件的环境可全量构建(KNOWN_ISSUES #20 备注)。
3. **[包化验证] nanosvg/stb 换 xrepo 前的核对项**:nanosvg 的 memcpy 边界修复是否含于所选版本;stb 头无版本宏,需人工对照文件头;`IRender.cpp:267-274` 的 IMPLEMENTATION 宏单 TU 方式与包安装头布局的兼容性(stb 需 `stb/` 前缀包含)。
4. **[同步纪律] 排除表双维护**:fork 根 xmake.lua 与 mlaunch `DuiLibLite` 的 `remove_files` 清单必须同步变更(现状一致);上游合并时按各 `LOCAL_CHANGES.md` 逐条对照(全库基线 = 34cf1e3 的 UTF-8 BOM 全量转换)。
5. **[可选] fork tests/ 最小基建**(KNOWN_ISSUES #18):一个 xmake test target + 编译期断言,golden 化 nanosvg/stb 行为,为将来换包提供回归门。

## 4. mlaunch 视角的一页备查

- mlaunch 不复制 DuiLib 源码,`third_party/DuiLib_DuiEditor` submodule → `DuiLibLite` 静态库(定义 `UILIB_STATIC`,xmake.lua:32/:113);升级 DuiLib = bump submodule 指针 + 跑 mlaunch CI(submodule 源码编译即回归)。
- mlaunch 实际用到的库面:`WindowImplBase/CPaintManagerWin32UI`(窗口与消息)、GDI 渲染后端、控件族(Button/Label/Edit/List/Layout)、pugixml(编入但运行时不用,见 02 篇 §7)、nanosvg+stb(SVG 图标,`IconManager::MakeSvgImageAttr` 路径)。
- 已知并接受的 fork 行为差异(见 02/03 篇与 KNOWN_ISSUES):`ITranslateAccelerator` 扩展、`MessageHandler` 死代码、NeedUpdate 不可见早退、缩放锁策略。
