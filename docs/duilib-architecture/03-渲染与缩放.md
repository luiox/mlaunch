## 1. 渲染后端选择与 GDI 双缓冲管线

### 1.1 后端工厂

后端枚举 `emRenderEngine`(`Render/IRender.h:40-46`,Default/GdiPlus/Sdl),静态保存在 `CPaintManagerUI::m_emRenderEngine`(Core/UIManager.h:630)。创建入口 `UIGlobal::GetRenderFactory`(Core/UIGlobal.cpp:34-59):

```cpp
switch (CPaintManagerUI::GetRenderEngineType())
{
case DuiLib_Render_Default:
    m_renderEngineFactory = MakeRefPtr<UIRenderFactory>(new UIRenderFactory_gdi);   // :41-43
    break;
case DuiLib_Render_GdiPlus: ...        // :44-46
```

mlaunch 从不调用 `SetRenderEngineType`,即始终走 **Default = 纯 GDI**;构建层面 SDL/Cairo 全组排除(mlaunch xmake.lua:42-47,与 fork 根 xmake.lua 排除清单同步)。gdiplus 后端仅当显式切换才启用。

### 1.2 UIRender_gdi:内存 DC + DIB section

`UIRender_gdi`(`Render/UIRender_gdi.cpp:133` 起)持有:

- `m_hDC`:与窗口 DC 兼容的内存 DC(`Init`,:147-182:`CreateCompatibleDC`);
- `m_curBmp`(`UIRender_gdi.h:72`):当前选入的后备位图,`CStdRefPtr<UIBitmap>`。

位图本体是 `UIBitmap_gdi`(`Render/UIObject_gdi.cpp:311-329`):

```cpp
bmi.bmiHeader.biHeight = bFlip ? -height : height;   // 负高 = top-down DIB(:321)
m_hBitmap = CreateDIBSection(hDC, &bmi, DIB_RGB_COLORS, (void **)&m_pBits, NULL, 0);  // :327
```

32bpp ARGB、可直接按 `m_pBits` 读写像素——`ClearAlpha`(:434-448)就是逐行 `memset` 4 字节/像素,把待绘区清成 0(透明黑),避免 DIB 残留脏数据。

`SelectObject` 对 `OT_BITMAP` 的处理(UIRender_gdi.cpp 内):`::SelectObject(m_hDC, pObject->GetHBITMAP())` 并把 `m_curBmp` 换成新位图。**`Init` 时先造一个 1×1 的 `m_defBmp` 选入**(:166-167/:178)——后备位图从 1×1 起步,第一次 `Resize` 才变成真实客户区尺寸。

### 1.3 OnPaint 主管线(UIManagerWin32.cpp:432-618)

```
WM_PAINT
 ├─ m_pRoot==NULL            → 空 BeginPaint/EndPaint 校验 (:434-440)
 ├─ m_bLockUpdate            → 仅 BeginPaint/EndPaint 校验,不绘制 (:447-455)  ← fork 修复②
 ├─ !GetUpdateRect(rcPaint)  → 无效区为空,直接返回 (:456-457)   ← 只取第一个矩形
 ├─ (m_bUpdateNeeded && !m_bLockUpdate)
 │    ├─ m_pRoot->SetPos(rcClient,true)  全树重排 (:484)
 │    └─ rcPaint = rcClient              强制整窗重绘 (:488)    ← fork 修复①
 │    (else 部分更新分支: __FindControlsFromUpdate 逐控件 SetPos :490-504)
 ├─ Render()->Resize(w,h)    后备位图对齐客户区 (:549)
 ├─ Render()->ClearAlpha(rcPaint)  清待绘区 (:551)
 ├─ GetRoot()->Paint(Render(), rcPaint, NULL)  控件树画进内存位图 (:573)
 │    └─ CControlUI::Paint → 裁剪 → DoPaint → Paint* 七步(UIControl.cpp:1704-1756)
 ├─ m_aPostPaintControls     顶层附加绘制 (:575-578)
 └─ ::BitBlt(m_hDcPaint, rcPaint..., SRCCOPY)  一次性上屏 (:601)
      EndPaint(:605) → 若绘制中又标脏则 Invalidate(:611)
```

要点:

- `m_hDcPaint` 是**窗口 DC**,`Init` 时 `::GetDC(hWnd)` 拿一次长持有(UIManagerWin32.cpp:116);
- `Render()->BeginPaint/EndPaint` 在 GDI 后端只是trace日志(UIRender_gdi.cpp:196-204),真正的 BeginPaint/EndPaint 在 OnPaint 内完成(:547/:605);
- **绘制恒定落进内存位图,屏幕只见一次 BitBlt**——这就是"双缓冲";`WM_ERASEBKGND` 返回 `lRes=1` 且窗口类 `hbrBackground=NULL`(UIManager.cpp:2621-2628、UIWindowWin32.cpp:227),系统不参与背景擦除,正常路径无闪烁。

### 1.4 后备位图生命周期

| 阶段 | 行为 | 位置 |
|---|---|---|
| 渲染器惰性创建 | `Render()` 首次调用时建 UIRender_gdi 并绑窗口 DC | UIManagerWin32.cpp:122-131 |
| 初始 | 1×1 `m_defBmp` 选入 | UIRender_gdi.cpp:166-167/:178 |
| 每次 WM_PAINT | `Resize(w,h)`:尺寸相同 no-op;不同则 `DeleteObject()` + `CreateARGB32Bitmap()` **销毁重建,不保留旧内容** | UIRender_gdi.cpp:235-249 |
| 绘制前 | `ClearAlpha(rcPaint)` 把待绘区清零 | UIManagerWin32.cpp:551 → UIObject_gdi.cpp:434-448 |

推论:**位图永远等于"上一次 Paint 时的客户区尺寸"**。窗口刚变大、还没走到 :549 之前,位图仍是旧尺寸——新扩出的区域在位图坐标系之外,谁也画不进去。这是理解缩放 bug 的第一块拼图。

## 2. resize 消息流全链(结合 mlaunch 实际代码)

mlaunch 的窗口类:`AppWindow : WindowImplBase`。类风格由 `WindowImplBase::GetClassStyle` 提供——**只有 `CS_DBLCLKS`,没有 `CS_HREDRAW/CS_VREDRAW`**(Utils/WinImplBase.cpp:49-52;`CWindowWin32::GetClassStyle` 同,Core/UIWindowWin32.cpp:17-20;注册处 `wc.style = GetClassStyle()`,UIWindowWin32.cpp:217-233)。

### 2.1 逐消息分解

```mermaid
sequenceDiagram
    participant User as 用户拖边框
    participant OS as Win32/DWM
    participant App as AppWindow(mlaunch)
    participant PM as CPaintManagerWin32UI
    participant R as UIRender_gdi

    User->>OS: 按住边框移动
    OS->>App: WM_ENTERSIZEMOVE(0x0231)
    App->>PM: LockUpdate(true)<br>app_window_interaction.cpp:490-493
    loop 每个 sizing tick
        OS->>App: WM_SIZE
        App->>PM: m_pm.NeedUpdate() 只标脏 (:507-512;库侧 UIManager.cpp:2742-2754 root 标脏)
        OS->>PM: WM_PAINT(系统只无效化"新暴露"条带,见 2.2)
        PM->>PM: 锁分支 :447-455 BeginPaint 校验后 return
        Note over PM,R: 不绘制、不 Resize 位图(:549 未到达)
    end
    User->>OS: 释放鼠标
```

mlaunch 侧源码(app_window_interaction.cpp):

- `0x0231 WM_ENTERSIZEMOVE` → `m_pm.LockUpdate(true)`(:490-493),注释"对齐原版:拖拽/缩放期间挂起重绘";
- `0x0232 WM_EXITSIZEMOVE` → `LockUpdate(false)` + `GetRoot()->NeedUpdate()` + `m_pm.NeedUpdate()` + `m_pm.Invalidate()`(:495-505);
- `WM_SIZE/WM_MOVE` → `m_pm.NeedUpdate()`(:507-517,只标脏)。

阴影窗口是挂在宿主窗口过程上的旁路监听(UIShadowWin32.cpp:164-209):父窗 WM_SIZE 时若**变大**则把 `Update()` 推迟到 WM_PAINT(:177-180 的注释明确记录了这个技巧),WM_EXITSIZEMOVE 再补一次 `Update()`(:204-209)。

### 2.2 关键机制:CS_HREDRAW/CS_VREDRAW 缺失意味着什么

Win32 规则:窗口类含 `CS_HREDRAW/CS_VREDRAW` 时,宽/高一变系统就**整窗无效化**;缺失时,系统只无效化几何上**新暴露出来的区域**:

- **向内缩小**:没有新暴露区域 → 系统不无效化任何像素 → 锁分支的 BeginPaint 校验一块空 region,旧帧完整留在屏幕 → 释放后全量重排+整窗 BitBlt 覆盖。视觉上"缩放期间旧帧微缩、结束瞬间换新帧",干净。
- **向外扩大**:右/下(或四周)**新增条带被系统无效化** → 这条带构成 WM_PAINT 的 update region。但:
  1. 锁分支(UIManagerWin32.cpp:447-455)`BeginPaint` 的副作用是**校验(清空)整个 update region**,然后什么都不画就 `EndPaint` + return;该分支在 `Render()->Resize`(:549)**之前**,后备位图保持旧尺寸——即便想画,新条带也在位图外(:243-244 的销毁重建只在上屏帧发生);
  2. 于是 sizing 期间新条带区域被"校验过但从未绘制",DWM 只能继续显示旧帧的 DWM 拉伸(模态 resize 时 DWM 对旧位图做边缘拉伸)或未定义像素;
  3. 直到 WM_EXITSIZEMOVE(:495-505)解锁 + 全量标脏 + `Invalidate()` 整窗(UIManager.cpp:735-742),下一帧才一次性补画。

**这就是"向内缩小没事、向外扩大出问题"的完整因果**:症状①(扩大方向区域不刷新)是锁分支吞绘制 + 无 CS_VREDRAW/CS_HREDRAW 的叠加;fork c329337 修复②("锁期间只校验不绘制")治好了当时的"DWM 拉伸闪烁"(KNOWN_ISSUES #2),代价是把闪烁换成了扩大方向的空白——同一枚硬币的两面。

### 2.3 释放瞬间的单帧积压(H2:卡顿)

WM_EXITSIZEMOVE 后的第一帧 WM_PAINT 要在一帧内完成(全部带行号):

1. 全树 `SetPos` 重排(:484)——列表 171 项时是可观开销;
2. 后备位图销毁重建(UIRender_gdi.cpp:243-244)——纯分配 + DIB 提交;
3. 整窗 `ClearAlpha`(:551,memset 全客户区)+ 全树 `Paint`(:573);
4. 整窗 `BitBlt`(:601);
5. 阴影窗口 `Update`(UIShadowWin32.cpp:204-209)——内部又一次 SetWindowPos + 区域重算。

sizing 期间一次都没画,全部工作压缩到这一帧,形成可感知停顿;若有原生 EDIT 子窗口(EditWnd)参与重排,其自绘(直接上屏,不走宿主位图)与本次 BitBlt 天然不同步,还可能出现 KNOWN_ISSUES #5 记录的黑块类现象(根因未定位)。

### 2.4 深层结构缺陷(修复底稿的"约束清单")

1. **无 resize 期降级绘制策略**:库内对 `WM_SYNCPAINT`(0x0088)零处理(仅 `DuiLib/compat.h:630` 有宏定义);sizing 期间要么全画(闪烁,H3),要么全不画(空白+卡顿,H1+H2),mlaunch 的 LockUpdate 只能在两者间二选一。
2. **脏区只取第一个矩形**:`GetUpdateRect` 单矩形(:456-459),复杂无效区会漏;部分更新分支还按陈旧 `m_rcItem` 画(#4)。
3. **`Invalidate` 无节流/合并**:`InvalidateRect(NULL,FALSE)` 直接打给系统(UIManager.cpp:735-742),重绘时机完全由 WM_PAINT 驱动——这在正常路径是优点(由系统合帧),在 resize 路径上则毫无帮助。
4. **位图全量重建**:UIRender_gdi.cpp:240-244 没有"原地扩容/保留旧内容"路径。
5. LockUpdate 是**纯绘制闸门**(m_bLockUpdate 只在 OnPaint 被读,:447/:469),不影响 WM_SIZE 标脏逻辑——所以"锁期间持续标脏、解锁帧集中重排"是当前设计的必然形态。

### 2.5 给 T3-A 的方向性提示(由 A 自行验证)

- 最小侵入方向:让**位图在 WM_SIZE 即时 Resize**、锁分支不再无条件吞绘制,仅绘制系统无效化的新暴露条带(条带之外维持旧像素,匹配 DWM 行为);
- 评估 `CS_HREDRAW/CS_VREDRAW`(整窗无效化换正确性,代价是 sizing 期间每 tick 的无效区变大)与处理 `WM_SYNCPAINT`(递归 resize 时同步绘制)的组合;
- 释放帧把"重排 + 位图重建 + 整窗 BitBlt + 阴影 Update"的合并/分期(如阴影延后一帧)作为卡顿项单独优化;
- 任何改动需保持"最小 diff、附实测场景"(fork KNOWN_ISSUES.md 修复原则),并注意锁分支同时被 mlaunch 的 WM_ENTERSIZEMOVE 路径依赖(app_window_interaction.cpp:490-493)——改库需同步检查宿主语义。
